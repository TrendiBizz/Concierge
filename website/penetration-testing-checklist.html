Penetration testing checklist

What to prepare, what gets tested and what a good report contains.

Scope a security review

How to use this checklist

This is the checklist we scope and test against. It combines the OWASP Web Security Testing Guide for web apps and APIs, the phase structure of the Penetration Testing Execution Standard and the planning, discovery, attack and reporting model in NIST SP 800-115. It is a working list, not a certification, and a tick here does not mean a system is secure. Ready to start? Scope a security review.

1. Before testing: scope and authorisation

  • ☐ Written authorisation from the owner of every system in scope (hosts, domains, apps, APIs, cloud accounts)
  • ☐ Scope list: exact URLs, IP ranges, environments (production or staging) and what is out of scope
  • ☐ Third-party services identified (hosting, payment, email, CDN) and whether their permission is needed
  • ☐ Test window, blackout periods and a named emergency contact on both sides
  • ☐ Rules of engagement: no denial-of-service, no data destruction, no social engineering or physical testing unless written in
  • ☐ Test accounts for each user role, or agreement to test unauthenticated only
  • ☐ Data handling: where findings and any captured data are stored, and when they are deleted
  • ☐ Backups taken and a rollback plan for anything that could change data
  • ☐ Compliance drivers noted (PCI DSS, SOC 2, ISO 27001, customer questionnaire) and the evidence format needed
  • ☐ Sign-off by both parties before the first request is sent

2. Information gathering and configuration

  • ☐ Map the application: pages, endpoints, parameters, technologies and versions
  • ☐ Search engine and public-source exposure (leaked files, old backups, exposed repositories)
  • ☐ Network and port review on the in-scope hosts
  • ☐ Web server and framework configuration, default files and admin interfaces
  • ☐ HTTP methods, security headers, TLS version and cipher configuration
  • ☐ Cloud storage and file-permission review
  • ☐ Subdomain takeover and forgotten staging or test hosts
  • ☐ Platform and dependency versions checked against known vulnerabilities

3. Identity, authentication and authorisation

  • ☐ Registration, account provisioning and role definitions
  • ☐ Username enumeration through login, reset and sign-up messages
  • ☐ Password policy, lockout and brute-force protection
  • ☐ Multi-factor authentication presence and bypass
  • ☐ Password reset, recovery and email-change flows
  • ☐ Default or weak credentials on admin and service accounts
  • ☐ Horizontal access: one user reading another user's records (insecure direct object references)
  • ☐ Vertical access: a normal user reaching admin functions
  • ☐ Directory traversal and path handling

4. Session management

  • ☐ Session token randomness, length and rotation after login
  • ☐ Cookie flags: Secure, HttpOnly, SameSite
  • ☐ Logout and session expiry on the server side
  • ☐ Session fixation and concurrent session handling
  • ☐ Cross-site request forgery protection on state-changing actions

5. Input handling and injection

  • ☐ SQL and NoSQL injection
  • ☐ Cross-site scripting: reflected, stored and DOM-based
  • ☐ Command, template and LDAP/XML injection
  • ☐ XML external entity processing
  • ☐ Server-side request forgery
  • ☐ HTTP request smuggling and host header injection
  • ☐ File upload type, size and storage checks
  • ☐ Open redirects and unvalidated forwards

6. Error handling, cryptography and data exposure

  • ☐ Error messages and stack traces that reveal internals
  • ☐ Sensitive data over unencrypted channels or in URLs, logs and caches
  • ☐ Weak or home-made cryptography, hard-coded keys and secrets
  • ☐ Padding oracle and weak hashing of stored passwords
  • ☐ Excess data returned by APIs compared with what the screen shows
  • ☐ Backups, exports and debug endpoints reachable from the internet

7. Business logic, client side and APIs

  • ☐ Workflow abuse: skipping steps, repeating actions, negative or oversized values
  • ☐ Price, discount, quota and rate-limit manipulation
  • ☐ Race conditions on payments, coupons and sign-ups
  • ☐ Client-side storage, postMessage, CORS and clickjacking
  • ☐ JavaScript source and source-map exposure
  • ☐ API authentication, object-level and function-level authorisation
  • ☐ API mass assignment, rate limiting and versioning leftovers
  • ☐ GraphQL introspection and query depth limits, where used

8. Reporting and retest

  • ☐ Each finding has a title, severity, affected URL, plain-English description and evidence
  • ☐ Steps to reproduce that a developer can follow
  • ☐ Practical fix guidance, ranked by risk and effort
  • ☐ Executive summary written for a non-technical reader
  • ☐ Scope, dates, limitations and what was not tested stated clearly
  • ☐ Debrief call offered to walk through the findings
  • ☐ Retest of fixed findings agreed and scheduled
  • ☐ All test data and accounts removed at the end of the engagement

9. What CREST expects, so you can hold any provider to it

CREST is a non-profit accreditation body for penetration testing companies and testers. Its CREST Defensible Penetration Test (CDPT) specification and its Guide to Penetration Testing (2022) describe how a test should be bought, scoped, delivered and signed off. The CDPT does not define a methodology or a list of things to test; for web and mobile apps CREST points to its OWASP Verification Standard (OVS), based on OWASP ASVS and MASVS. We do not claim CREST accreditation (see our penetration testing page). We list these expectations because they are a sound way to judge any provider, including us.

Three phases

  • ☐ Scoping: goals and objectives written down, full relevant attack surface described, scope agreed by a suitably skilled person
  • ☐ Delivery: the work covers every element in the scope; any constraint that stopped full coverage is documented
  • ☐ Sign-off: a named, qualified person or company officer attests the test followed the provider's methodology and the agreed scope

Scope statement (CREST Guide, Part 4)

  • ☐ Systems in and out of scope
  • ☐ Testing approach: black-box, grey-box or white-box
  • ☐ Prohibited tests, such as denial of service
  • ☐ Where the testers work from, and the testing days and times
  • ☐ Approvals needed before testing starts
  • ☐ Who leads the test, and the named testers with their roles, skills and qualifications
  • ☐ Report format, delivery date (within a few days of finishing) and delivery method
  • ☐ How affected third parties and your own staff will be told, so a test is not mistaken for a real attack
  • ☐ Statement signed off by all relevant parties

Minimum report contents (CDPT, section 10)

  • ☐ Goals and objectives of the assignment
  • ☐ Scope, including location, exclusions, restrictions and the coverage actually gained
  • ☐ Full results of the test
  • ☐ A timeline of key activities, with logs available on request (accounts modified, files executed, access attempts that succeeded or failed)
  • ☐ Enough detail for you to understand and reproduce each issue
  • ☐ Each vulnerability risk-assessed against an agreed method, with a CVSS severity score
  • ☐ Remediation advice for every vulnerability
  • ☐ A statement of totality against the defined scope
  • ☐ Identity and qualifications of the people who scoped, delivered and signed off the test
  • ☐ How to raise a complaint with the accrediting body, where the provider is accredited

Before you buy

  • ☐ Ask whether the provider is accredited, by whom and for which discipline, and check that with the accrediting body directly
  • ☐ Ask which named testers will do the work and what practical (lab-based) qualifications they hold
  • ☐ Ask for a sample report using your preferred severity scheme
  • ☐ Ask where your data is kept and how it is securely deleted after the test
  • ☐ Ask how a fixed finding is retested, and whether that is in the quote

Source: CREST, CREST Defensible Penetration Test (2023 edition, v5.2) and A Guide to Penetration Testing (2022), read 25 November 2026. This summary is ours, not CREST's. CREST documents are the authority; check them for current wording.

What this checklist does not cover

Social engineering, physical security, wireless and internal-network testing are not part of a standard web engagement. They are scoped and priced separately in writing, as set out on the penetration testing page. For a lighter, informational pass use the website security check. If you need a certified third-party report for a compliance audit, we will say so before you pay for anything.
