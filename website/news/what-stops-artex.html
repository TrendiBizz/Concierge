What Actually Stops ARTEX: Code Review and Nine Incidents

By Trendi, Published 27 November 2026

In November, the FBI warned about ARTEX, an open-source AI hacking tool where AI agents run penetration tests themselves. A security team analysed the ARTEX system and its source code without running it, and checked it against nine public incident write-ups from Bitrise, Google, Microsoft and others. This is the result. ARTEX's own screenshot shows a rule blocking data leaving the target switched on; in the shipped version, it is off.

How ARTEX works

ARTEX's web console resembles a project-management app, not a hacker's terminal. Operators open a chat, pick an agent and enter a plain-English goal (e.g. getting into example-corp's back office to see whether customer data can be read). ARTEX splits that goal into steps and graphs goals, intended tries, facts and confirmed weaknesses. A main agent passes operator hints; a planner picks next steps; workers (three by default) run jobs and report back. All share one record, rating findings high, medium or low.

Agents use ordinary tools (command line, browser and standard network tools) with no exploit library. Capability comes from any model speaking Anthropic's or OpenAI's interface, so better models upgrade ARTEX without code changes. A dashboard tracks token cost; Check Point puts real criminal campaigns at about $150 to $1,500 each.

Underneath sits norma, a general-purpose agent engine by the same developer, plus a rule guard and recording proxy. ARTEX is about 60,000 lines of Go plus a similar-sized TypeScript console, norma adds 19,000 lines of Go, and a test suite is roughly half that size. Agent instructions and some comments are in Chinese.

What its own code will and won't stop

The norma engine includes an approval step, the 'are you sure?' pause before risky actions. ARTEX switches it off for every agent, leaving only its guard and a short rule list.

Those rules stop obvious damage like wiping disks. A code comment notes the data-leaving check was once built into the guard, then turned into a deletable rule shipped off because it 'mis-fires' on legitimate penetration-testing transfers. Out of the box, ARTEX avoids breaking systems while nothing stops it taking data.

Operators can set scope, yet limits are checked only when recording targets, never against executed commands. A detection engineer testing his home network told ARTEX not to change his TV's settings; it still sent write requests.

Workers are told a block, filtered request or 'not found' never exhausts a route, prompting retries past firewalls. Every agent is told it belongs to an authorised penetration-testing system, explaining its polite labels. Contrary to Amazon's account, neither checked version has a separate verification agent; the planner checks its own goals. Whatever stops ARTEX won't be ARTEX.

What the Bitrise incident shows

Bitrise's November report is the most detailed public account, covering a platform about 8,500 teams use to build and ship mobile apps. From 25 October, ARTEX scanned three days, sending more than 36,000 requests from one address, many labelled 'authorized-pentest' with none ordered. Bitrise's verdict: traffic that 'calls itself an authorized test, when you ordered none, is an attacker introducing itself.'

It returned on 12 November with more than 48,000 requests in about six hours. Next day, two minutes after failed sign-ins on three other bots, it entered via a privileged internal test account unused since 2022 with no two-factor authentication. It read unprotected build secrets and used a stolen cloud key 10.5 minutes after sign-in.

Bitrise spotted it about 4 hours 46 minutes after first sign-in and took its platform offline hours later, noting 'issued tokens keep working' after disabling a key. Logs also showed norma/0.4, hard-coded in norma's web fetch tool. Controls still held: a metrics-only key was refused everything, requests for other customers' data got nothing, and every request failed when the attacker returned on 18 November.

Patterns across nine incidents

Across the other eight write-ups (Railway, WorkOS, Barracuda, Microsoft, Datadog, Google, Amazon and Check Point), entry is nearly always a credential or forgotten system, rarely a new exploit, travelling through machine credentials (keys and tokens software uses).

Leak-to-use takes minutes: Microsoft saw a GitHub secret reach Azure Key Vault data in about five minutes. Google saw retries under new file names and counted nearly 500 throwaway web addresses carrying data out. Google says these tools 'currently trade stealth for velocity' and expects that to change, yet future versions still need a working credential and unwatched system.

A check you can run today

Search web and API logs for user agents containing 'pentest', 'authorized' or 'norma', and check whether anyone booked that test.

Two limits apply: the mid-November release sends ordinary browser user agents (so this mainly catches older copies and past visits), and it needs logs: the detection engineer found most of his internal apps did not log web requests.

The 30-day plan

Complete four independent workstreams within 30 days, ideally a fortnight, before the holidays, ranked by how many of the nine incidents each answers:

  1. Machine credentials (platform team): Find long-lived keys and build-pipeline tokens; replace the riskiest with short-lived workload-tied credentials (workload identity federation on Google Cloud, roles on AWS, managed identities on Azure); scope the rest and mark build secrets protected. Answers seven of the nine write-ups.
  2. Detection (SOC): Deploy four alerts while other work runs: (a) credentials used outside your networks and cloud ranges (Bitrise says this rule matches every stolen-key use in its advisory); (b) a secret exposed with any credential used from a new address within the hour; (c) a burst of failures then a success; (d) traffic claiming to be an unbooked authorised test. Log internal-app web requests and watch for 'norma' and 'artex-probe'.
  3. Accounts and exposure (identity and infrastructure): Disable dormant, test and supplier accounts and former suppliers' keys; enforce two-factor authentication on everything left; take admin consoles, build systems and cloud management endpoints off the open internet; close forgotten endpoints.
  4. Data leaving and incident response (security architecture and IR): Apply egress allow-lists to build servers and back ends, rate-limit bulk send/export and log secret reads. Write a revocation runbook listing where each important key is honoured, how to kill it there and a fixed window for judging damage (learned the hard way by Bitrise and Railway).

When commissioning AI-driven testing, ask whether scope is enforced in the network or 'only in a prompt'. One untested idea: ARTEX reads server responses without treating them as data, so a notice on your own systems might tell an agent to stop; keep any test to your own systems and check with legal.

What to tell your board

The tool is cheap, fast and noisy, and it gets in through old credentials and forgotten systems rather than anything exotic. Changes are underway to replace long-lived keys, closing old accounts and exposed consoles, and watching for keys used in the wrong place.

Key takeaways

  • From the code: Approvals are off, the data-leak rule ships off and scope relies on model manners, so your controls do the stopping.
  • From your logs: Traffic claiming an unbooked authorised test warrants checking today, but names will change; keep logs and alert on credentials used unexpectedly.
  • From nine incidents: ARTEX enters via credentials and forgotten systems and moves in minutes; replace long-lived credentials first and deploy that alert before any other.
