# N11 production observability — in progress

Cause: text logs lack request correlation and public readiness has no independently monitored endpoint.
Fix: privacy-minimising JSON logs, validated request IDs, optional Sentry SDK with a strict event allowlist, current readiness at /status, external GitHub probes include status and healthz. Sentry is disabled without SENTRY_DSN. No accounts created or money spent.

Limits: /status is a JSON readiness resource on the production host, not an independent historical status page. Dedicated status hostname, external status publication, background exception aggregation and full tenant/call context propagation remain outstanding. The formatter accepts numeric/UUID tenant and call IDs on explicit log records; existing call paths do not yet populate all of them.

Jo must supply: approved Sentry/GlitchTip project DSN and data-processing approval; an independent status host/provider and DNS access; a pre-funded standby host or managed Postgres instance and credentials. Do not enable paid services automatically.

Warm-standby procedure (not executed against an unprovisioned host):
1. Provision only with Jo-supplied infrastructure. Keep standby outbound workers and telephony disabled; never run two active schedulers.
2. Restore the encrypted backup into an isolated database using the existing restore-test.sh workflow. Validate tenant/message counts and migration revision; record backup age as measured RPO.
3. Deploy the same committed revision using deploy-api.sh, deploy-site.sh and sync-tooling.sh with VPS_HOST pointing to the standby. Tag a rollback image before every deployment. Hold the global deploy lock throughout merge/deploy/verification.
4. Validate /healthz, /widget.js, seo-gate.sh and verify-deploy.sh against standby. Run the deep health check. No real SMS, calls or mail replay.
5. Fence the primary's outbound workers before switching database or traffic. Jo supplies DNS/SIP routing control. Measure elapsed recovery time as RTO; no RPO/RTO claim before a real drill.
6. If checks fail, keep traffic on primary. After cutover, reverse traffic only after fencing standby and checking database divergence; never blindly switch to stale data.
