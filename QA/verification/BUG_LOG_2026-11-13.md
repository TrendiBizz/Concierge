# Bug log — 2026-11-13 (session 20)

Required by the permanent bug rule in `~/.dsh/AGENTS.md` and the repo `AGENTS.md`: every defect
found is fixed, tested and documented in the same session. No "come back later". This file is the
record for this date. Each entry gives the cause, the fix, and the evidence that the fix works.

An entry is only closed when all three are present. Anything in the "Open" section is a bug whose
fix is blocked by something outside our control, with the blocker named — never a shrug.

---

## 1. SVG logos rendered without their lettering

**Cause.** `resvg` resolves an exact font family and never falls back. The container had no
`Liberation Sans`/`DejaVu Sans`, so `font-family="Arial,sans-serif"` produced a logo with the
wordmark silently missing. The old reader would have stored that blank image as "their logo".

**Fix.** `fonts-liberation` in `Dockerfile.api`, `resvg_py==0.5.0` pinned in
`api-requirements.lock`, and the reader *measures* whether text drew against a baseline forced to
use an impossible family, reporting "as intended" / "redrawn in a close match" / "words missing".

**Evidence.** `QA/verification/BRAND_FROM_SITE_2026-11-13.md`. With no font: wordmark 0 px of ink.
With the font: 512×137, 6043 bytes, 13,119 px of ink. Live container: all four trendibizz logos
render. 38 tests in `api/tests/test_brand_from_site.py`.

## 2. The reader claimed a colour from an image that never drew

**Cause.** Accent extraction ran on the rasterised bytes without checking whether the render
succeeded, so a blank logo could still yield a colour, and the screen said "found it" about an
image the customer would never see.

**Fix.** `render_logo_svg` returns the text state, and the accent is only proposed from an image
that actually contains the brand; otherwise the note says so plainly.

**Evidence.** Three specific honesty failures were reproduced against the real site and pinned in
`test_brand_from_site.py` (accent only from a real render; NZ inferred from page wording, not just
the TLD; the note no longer says "choose one below" when nothing rendered).

## 3. Deploy script rolled back a good deploy

**Cause.** `run_s20a.sh` ended on `docker logs | grep -ci traceback`, which exits 1 when it finds
nothing. The `ERR` trap fired on that success case and re-tagged `:vps` to the old image and copied
old files back, while the new container kept running.

**Fix.** No `ERR` trap in deploy scripts. Every check is explicit and sets `OK=0`; the script ends
on `RESULT: OK`. Written up in the handoff.

**Evidence.** `run_s20b.sh` and the later inline deploys: `RESULT: OK`, image id and running
container id compared and equal, health `healthy`, `social` recreated and attached.

## 4. The healthcheck re-emailed the same condition

**Cause.** `plan_notifications` (then inline in `main()`) keyed its "already told them" check on
`status|detail`. When the detail grew from `consent` to `consent,mailbox` the key changed and the
operator got another identical-looking `[Concierge FAIL] inbound:chain` email. Two arrived 20
minutes apart.

**Fix.** Claim on the status alone; a detail change updates what the next reminder says, silently.

**Evidence.** `api/tests/test_healthcheck_notifications.py`, 6 tests. Mutation check performed: with
the detail put back into the key, `test_a_wordier_detail_does_not_email_again` fails; restored, it
passes. Live after deploy: `state.json` keeps `last_sent` unchanged and no new email is sent.

## 5. Two portals demanded a password, and the sign-in asked for an unknown "Business ID"

**Cause.** Invitation flow required inventing a 12-character password typed twice, then signing in
with an email plus a Business ID the customer had never been shown. `/owner-ui` had its own
separate password form, so any account opened by a future link would have been locked out of it.

**Fix.** The invitation link signs the customer in on arrival, with no password (`password_hash =
"no-password"`, which `verify_password` can never match), a 30-day session kept in local storage,
and an email-a-link fallback for returning visits. `/owner-ui` opens from the same link. The answer
for an unknown address is identical to a known one, so the endpoint cannot probe customers.

**Evidence.** `api/tests/test_passwordless_login.py` (9 tests). Live on the scratch
`trendi-meta-review` tenant: link redeemed → session issued → `/owner/me` answered → replay
refused with 400 → old sessions dropped. Bundle check: the password form is gone from the served
entry chunk.

## 6. Granting email consent did not switch the inbox on

**Cause.** Consent was recorded and nothing re-enabled the reply mailbox. A mailbox registered
before the owner consented stayed `enabled = false`, so the customer granted permission, saw no
error, and their mail was still refused. The operator then fixed it by hand with SQL.

**Fix.** `POST /owner/onboarding/authorizations` re-ensures the reply address when `email_read` is
granted. A Cloudflare or routing failure is reported in the response but never loses the consent.

**Evidence.** `api/tests/test_consent_enables_mailbox.py` (5 tests: granted, no reply address,
unrelated channel, withdrawal, routing failure). Live: `trendi-support` is the one mailbox still
disabled, and it is waiting for the owner's own click — we do not write consent for a customer.

## 7. Setup never asked for the permissions the customer needs

**Cause.** The finish step pointed at "the workspace" for permissions, so a customer could leave
onboarding with email and phone switched off and no idea why nothing worked.

**Fix.** The finish step carries the capability cards — email, phone, recording, texts, social —
each stating what we do, what data it touches and how to undo it, granted by the owner's own click.
Invitees land on Setup rather than an empty dashboard, and finishing setup no longer reloads the
page.

**Evidence.** Build passes; the served entry chunk contains the capability copy and the "Yes,
allow this" action; the consent-to-mailbox path is covered by entry 6. **Not yet walked in a
browser** — see Open below.

## 8. A deploy command ran with no destination host

**Cause.** I set `SSH="ssh $SSHO"` without `root@…`. Every remote step then ran `ssh <command>`,
failing with "hostname contains invalid characters", while a separate correct `scp` had already
copied the file. The deploy half-happened: new file on disk, no build, no swap.

**Fix.** Rewritten with the host in the variable; the build and swap then ran and were verified
(image id, running container id, health, social attachment).

**Evidence.** `vps tag sha256:ceb32…` = `running sha256:ceb32…`, api healthy, social network mode
equal to the api container id, 0 tracebacks. Rule recorded: check `SSH` contains `root@…` before
trusting a deploy.

## 9. A component replacement silently deleted a helper

**Cause.** I replaced `Login`/`Invite` by slicing the file between two markers; the slice also
removed `money()`, which lived between them.

**Fix.** Restored from git and rebuilt.

**Evidence.** `tsc -b` caught it (`Cannot find name 'money'`) before any deploy; the build is a
gate in every deploy script. The catch is the point: the type check found it, the deploy never saw

## 10. Verification grepped a stale bundle

**Cause.** The check used `ls assets/index-*.js | head -1`, which is an arbitrary chunk. Old chunks
survive because the portal rsync does not use `--delete`. The check reported 0 matches for strings
that were in fact deployed, which briefly looked like a failed deploy.

**Fix.** Read the entry script from `index.html`, then grep that file.

**Evidence.** Entry-based checks returned 1 for every expected string, and correctly 0 for the
removed password form.

## 11. A human takeover answered every visitor with a 502

**Cause.** `run_turn` returns on a takeover with `{reply, suppressed, reason, conversation_id}`.
`/api/v1/chat` then reads `result["lead_captured"]`, `result["booking_url"]` and
`result["appointment"]`. Those keys were absent, so the endpoint raised `KeyError`, the handler
turned it into `HTTPException(502)`, and the widget showed "The assistant is temporarily
unavailable". A takeover — the feature meant to make the owner sound human — looked like an outage.

**Fix.** One `chat.suppressed()` shape, used by the takeover path and the new pause path.

**Evidence.** `test_a_human_takeover_returns_the_full_shape` in `api/tests/test_tenant_pause.py`.
Mutation check: restoring the four-key result makes that test fail.

## 12. My own verification script reported a false failure

**Cause.** The live pause check counted rows in a table called `enquiries`, which does not exist.
Postgres returned an error string, `int()` on it yielded 0, and the script printed "lead NOT kept".
The product was correct; the instrument was wrong — and it accused the product of a real-sounding
bug.

**Fix.** Query `leads` and `enquiry_sources`, which is what `enquiries.capture` writes.

**Evidence.** Re-run against production: 2 `leads` rows for the tenant, one from the paused turn and
one from the resumed turn, each with its source row.

## 13. My pause gate changed the reason a suppressed address reports

**Cause.** I placed the outbox pause check before the suppression and takeover checks, so a
suppressed address reported `tenant_paused` instead of `address_suppressed`. The existing
`test_email_reply_to` caught it.

**Fix.** The gate now sits after the specific checks and immediately before the channel dispatch, so
the more specific reason wins and nothing is sent either way.

**Evidence.** `api/tests/test_email_reply_to.py::test_suppressed_address_is_never_sent_to` passes.
976 tests pass.

## 14. The Contacts tab returned 500

**Cause.** `ORDER BY COALESCE(last_at, c.updated_at)` used a *select alias* inside an expression.
Postgres permits an alias only as a bare ORDER BY item; at prepare time it fails with
`column "last_at" does not exist`. Every request to `/owner/contacts` was a 500 — the tab had
never worked in production.

**Fix.** Repeat the subquery in the ORDER BY.

**Evidence.** Reproduced and fixed against a real Postgres 16 with the real `schema.sql`: old SQL
errors, new SQL returns rows. Live: `/owner/contacts` 200. Standing check:
`scripts/verify/probe_owner_routes.py`.

## 16. Every logo silently failed to render in production

**Cause.** Two faults compounding. The API image was built from a **stale**
`scripts/vps/api-requirements.lock` on the server that had no `resvg_py`, so no SVG could be
rasterised; and `rasterise_svg` swallowed the ImportError and returned `None`, so the failure was
invisible. The owner was shown "We found a logo on your site but could not turn it into an
image", blaming their website for our missing dependency.

**Fix.** The repo's lock and `Dockerfile.api` are deployed to the box and the image rebuilt from
them; and a missing renderer now logs once, loudly, instead of returning silence.

**Evidence.** In the rebuilt image `resvg_py` renders a 169-byte PNG test and Liberation fonts are
present. Live `brand-suggestion` for our own site returns a 9,873-byte logo, and the review screen
draws 5 of 5 images. Tests: `api/tests/test_logo_renderer_present.py` (2), mutation-checked.

## 17. A typed website was rejected at save, so setup could not be completed

**Cause.** The reader accepts `trendibizz.com`; `OwnerBusinessProfile.website_safe` required a full
`https://` URL and answered 422 for the same text. The customer read their site successfully, then
could not save the review screen — a dead end at the last step of onboarding.

**Fix.** The validator normalises as `normalise_site` does (prefix `https://`, upgrade `http://`)
and keeps every safety rule.

**Evidence.** `api/tests/test_profile_website_normalised.py` (10), mutation-checked; live PATCH now
returns 200 and stores `https://trendibizz.com`; the Playwright setup run now reaches the install
step and the capability cards.

## 18. The chat widget silently disappears on a site with a strict CSP

**Cause.** Our own site loads `widget.js` (200) and it requests `widget-config`, but the page's CSP
(`style-src 'self'`, `script-src` without inline) blocks the inline style and script the widget
injects. The widget fails silently — no launcher, no message, no console error a customer would
understand.

**Not fixed in-session — blocked on a decision, deliberately.** The only fixes are to relax the
marketing site's CSP (`'unsafe-inline'` for styles) or to change the widget to load an external
stylesheet instead of injecting one. The first weakens a public security header; the second changes
the embeddable widget. Both need the operator's call.

**Evidence.** Playwright console capture on https://trendibizz.com/:

```
Executing inline script violates ... 'script-src 'self' https://static.cloudflareinsights.com https://chat.trendibizz.com'
Applying inline style violates the following Content Security Policy directive 'style-src 'self''
```

The CSP is served from `/website/site/_headers` inside the website container, which is **not in this
repo** — so it is also an instance of server drift.

**Next action.** Operator decides: relax `style-src`, or make the widget CSP-friendly. Either way,
document the required directives in the install instructions, because any customer site with a
strict CSP loses the widget the same silent way.
