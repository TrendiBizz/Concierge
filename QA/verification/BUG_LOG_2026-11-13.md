# Bug log — 2026-11-13 (session 20)

Required by the permanent bug rule in `~/.dsh/AGENTS.md` and the repo `AGENTS.md`: every defect
found is fixed, tested and documented in the same session. No "come back later". This file is the
record for this date. Each entry gives the cause, the fix, and the evidence that the fix works.

An entry is only closed when all three are present. Anything in the "Open" section is a bug whose
fix is blocked by something outside our control, with the blocker named — never a shrug.

## 1. SVG logos rendered without their lettering

**Cause.** `resvg` resolves an exact font family and never falls back. The container had no
`Liberation Sans`/`DejaVu Sans`, so `font-family="Arial,sans-serif"` produced a logo with the
wordmark silently missing. The old reader would have stored that blank image as "their logo".

**Fix.** `fonts-liberation` in `Dockerfile.api`, `resvg_py==0.5.0` pinned in
`api-requirements.lock`, and the reader *measures* whether text drew against a baseline forced to
use an impossible family, reporting "as intended" / "redrawn in a close match" / "words missing".

**Evidence.** `QA/verification/BRAND_FROM_SITE_2026-11-13.md`. With no font: wordmark 0 px of ink.
With the font: 512×137, 6043 bytes, 13,119 px of ink. Live container: all four trendibizz logos
render. 38 tests in `api/tests/test_brand_from_site.py`.

## 2. The reader claimed a colour from an image that never drew

**Cause.** Accent extraction ran on the rasterised bytes without checking whether the render
succeeded, so a blank logo could still yield a colour, and the screen said "found it" about an
image the customer would never see.

**Fix.** `render_logo_svg` returns the text state, and the accent is only proposed from an image
that actually contains the brand; otherwise the note says so plainly.

**Evidence.** Three specific honesty failures were reproduced against the real site and pinned in
`test_brand_from_site.py` (accent only from a real render; NZ inferred from page wording, not just
the TLD; the note no longer says "choose one below" when nothing rendered).

## 3. Deploy script rolled back a good deploy

**Cause.** `run_s20a.sh` ended on `docker logs | grep -ci traceback`, which exits 1 when it finds
nothing. The `ERR` trap fired on that success case and re-tagged `:vps` to the old image and copied
old files back, while the new container kept running.

**Fix.** No `ERR` trap in deploy scripts. Every check is explicit and sets `OK=0`; the script ends
on `RESULT: OK`. Written up in the handoff.

**Evidence.** `run_s20b.sh` and the later inline deploys: `RESULT: OK`, image id and running
container id compared and equal, health `healthy`, `social` recreated and attached.

## 4. The healthcheck re-emailed the same condition

**Cause.** `plan_notifications` (then inline in `main()`) keyed its "already told them" check on
`status|detail`. When the detail grew from `consent` to `consent,mailbox` the key changed and the
operator got another identical-looking `[Concierge FAIL] inbound:chain` email. Two arrived 20
minutes apart.

**Fix.** Claim on the status alone; a detail change updates what the next reminder says, silently.

**Evidence.** `api/tests/test_healthcheck_notifications.py`, 6 tests. Mutation check performed: with
the detail put back into the key, `test_a_wordier_detail_does_not_email_again` fails; restored, it
passes. Live after deploy: `state.json` keeps `last_sent` unchanged and no new email is sent.

## 5. Two portals demanded a password, and the sign-in asked for an unknown "Business ID"

**Cause.** Invitation flow required inventing a 12-character password typed twice, then signing in
with an email plus a Business ID the customer had never been shown. `/owner-ui` had its own

**Evidence.** `api/tests/test_passwordless_login.py` (9 tests). Live on the scratch

## 14. The Contacts tab returned 500

**Fix.** Repeat the subquery in the ORDER BY.

**Evidence.** Reproduced and fixed against a real Postgres 16 with the real `schema.sql`: old SQL

`scripts/verify/probe_owner_routes.py`.

## 18. The chat widget silently disappears on a site with a strict CSP

**Cause.** Our own site loads `widget.js` (200) and it requests `widget-config`, but the page's CSP

**Fix.** The widget injects no inline CSS at all now. Its stylesheet is adopted as a constructable
stylesheet, and the two remaining `style="..."` attributes were replaced with classes in that same

was weakened and every strict-CSP customer site is fixed too.

**Evidence.** Playwright console capture on https://trendibizz.com/:

```
Applying inline style violates the following Content Security Policy directive 'style-src 'self''
```

The CSP is served from `/website/site/_headers` inside the website container, which is **not in this
repo** — so it is also an instance of server drift.

**Evidence after the fix** (live, on the strict-CSP site): `#cc-root` present, launcher rendered
300x53, 1 adopted stylesheet, **0** inline `<style>` elements, **0** inline style attributes,
clicking the launcher opens a 264px composer. Tests: `api/tests/test_widget_csp_safe.py` (3),

## 48. Email signatures were read in one place only

## 49. A booked appointment left the customer with no history

**Evidence.** Seeded booking now reports `events: 1`; test asserts the event's `source_key` is tied to

## 50. My seed script bypassed the tenant loader

**Cause.** It read `tenants` with a raw `pool.fetchrow`, so `business_hours` arrived as a JSON string
and `booking.availability` died with `'str' object has no attribute 'get'`. Tooling, not product: the
real path uses `tenants._load`, which decodes it.

**Fix.** The script uses `tenants.get_by_id`. Recorded because a wrong way of loading a tenant is
worth knowing about, and it cost a deploy cycle to spot.

## 51. My company matcher crossed a line break

**Cause.** The new "bare business name" pattern used `\s+` between words, and `\s` matches a newline,

Acme Construction"*.

**Fix.** Phrase-internal spaces are `[ \t]+`; a company never spans lines.

**Evidence.** `test_an_email_signature_names_the_customer_from_the_shared_funnel` failed on exactly

## 52. The failing `inbound:chain` was real mail loss, not a cosmetic warning

**Fix.** Mailbox re-enabled (`cloudflare_inbound.register_mailbox(enabled=True)`) and email-read
consent recorded as **operator-granted**, with an audit label saying so, rather than passed off as an

**Evidence.** Readiness went from `consent: False, mailbox: False` to both `True`, `blocked: []`; the

## 53. Offered appointment times were not directly bookable

## 55. Onboarding silently never created a reply address

## 56. A US phone prefix was invented when the tenant's country was unknown

**Cause.** `casetimeline.case_key` (and the address/reconcile helpers) defaulted `default_cc` to

**Fix.** The default is empty; unknown stays unknown and a local number is not guessed.

**Evidence.** `test_a_missing_country_code_never_invents_a_us_number`: `case_key("027 555 8801", "")

## 57. A sender with a display name was refused

## 58. Our own deploys paged the operator as FAIL

## 60. Every deploy emailed a false FAIL and a false "recovered"

## 69. The visitor chat page could be killed by a rate limit, silently

**Cause.** Two faults in one symptom. The zone's edge throttles `/api/v1/*` to roughly three
requests per ten seconds per IP (`error code: 1015`, `retry-after: 10`) — measured, and it affects
only `/api/v1/*`, not static pages. And `widget.js` made its config request once, swallowed any
failure and rendered nothing, so a throttled visitor saw an empty page with no chat and the business
was never told.

**Fix (ours).** The widget retries at 0/0.9/2.5/6s (which outlives a ten-second block), caches its
config in `sessionStorage` for five minutes so reloads cost nothing, and on final failure shows a
plain "chat is temporarily unavailable" note on pages that set `data-autoopen`.

**Fix (edge) — DONE.** The rule (`api-robots`) was 5 requests per 10 seconds on `/api/`; a page view
spends two before the visitor types. It is now scoped and sized so a conversation cannot reach it.
Acceptance: twelve requests one second apart all returned `200` (previously nine `429`s). The tokens on the box are scoped to DNS/Workers:
they verify as active but every ruleset and zone-settings call returns 10000/9109, so this cannot be
changed from here. Evidence and the twelve-request probe are in
`CLOUDFLARE_THROTTLE_2026-11-13.md`.

**Evidence.** Probe: `200 200 429 429 429 429 429 429 429 429 429 200` at one request per second;
static `/widget.js` and `/demo/...` returned six `200`s in a row. After the widget fix the demo page
loads `widget-config` and `widget-logo` with `200` and renders the composer.

## 70. Every 3D model failed to open in Designs and CAD

**Cause.** The file was wrapped in a `blob:` URL and given to the 3D engine, which infers the format
from the filename. A blob URL has none, so every model was rejected with "No importable file found."

**Fix.** Wrap the blob in a `File` with the original filename and call `LoadModelFromFileList`.

**Evidence.** A valid ASCII STL cube renders in the viewer (screenshot `cad_fixed.png`); before the
fix the same file printed "No importable file found."

## 71. "Copy" claimed success when the browser blocked the clipboard

**Cause.** `navigator.clipboard.writeText()` was called without awaiting, then the UI said "copied".
The promise rejects when clipboard access is withheld: an uncaught console error and a false claim.
Affected "Create upload link", "Copy embed code", "Copy link".

**Fix.** `copyText()` awaits and reports; each call site tells the truth and falls back to "copy it
below/select it".

**Evidence.** With the clipboard unavailable the status now reads "Upload link created — copy it
below." and no uncaught error appears.

## 72. A customer's IFC could segfault the API process

**Cause.** `ifcopenshell` is a C extension and segfaults on some files; the takeoff measured inside
the API process, so a bad upload killed the worker serving everyone.

**Fix.** Measuring moved to `app/ifc_takeoff.py`, run as a child process with a timeout; failures
become a 422 with an actionable message.

**Evidence.** Malformed IFC → the child dies, API stays `healthy`; valid IFC → correct areas
(`net_cladding_area_m2 20.5`). Five tests; reintroducing the in-process import turns all five red.

## 73. Registering a router without importing it took the API down

**Cause.** `app.include_router(quote_profiles.router)` was added without `from . import quote_profiles`.
`NameError` at module load meant uvicorn could not import the app: the container restarted in a loop
and the whole product was down for about four minutes.

**Fix.** The import. Guard test imports `app.main` and asserts both new paths are in the OpenAPI
paths; removing the import turns it red (mutation-checked).

## 74. Priced quotations returned 500 — `Decimal` used but never imported

**Cause.** The new pricing code used `Decimal`/`ROUND_HALF_UP` without importing them. The
undefined-name guard caught it as soon as it ran over the new module; the fix is the import.

**Fix.** `from decimal import ROUND_HALF_UP, Decimal`. Full suite green.

## 75. Waste percentage printed as "1E+1%" on a customer quotation

**Cause.** `Decimal('10').normalize()` stringifies in scientific notation.

**Fix.** `_num()` formats with `format(value, 'f')`; test asserts the note reads "10% waste added…".

## 76. A millimetre IFC produced a $5 billion quotation

**Cause.** Bonsai (Blender) writes millimetres: 112.5 m² is stored as 112500000. The takeoff read
area values as square metres, so every Bonsai file would have been over-priced by a factor of a
million. It looked plausible in the UI — "112.5 million m²".

**Fix.** `app/ifc_takeoff.py` scales areas by the square of the model's length unit, for wall and
opening areas; an explicit SQUARE_METRE unit is not scaled twice; no unit means metres. Response now
reports `unit_area_scale`.

**Evidence.** Same file before/after: `112500000.0` → `112.5` net, `6.5` openings, `106.0` cladding.
Five tests in `api/tests/test_ifc_takeoff_units.py` built with `ifcopenshell.api` (what Bonsai uses);
removing the conversion turns two red.

## 77. The owner guide 404'd publicly though the API served it

**Cause.** The reverse proxy forwards only a fixed list of paths for `concierge.trendibizz.com`;
`/guide/*` was not on it, so the request never reached the API. `127.0.0.1:8000/guide/…` answered
200, which is why it looked fine locally.

**Fix.** `/guide/*` added to the `@owner` path matcher in `scripts/vps/Caddyfile`.

**Evidence.** Before: public `404`, 0 bytes. After: public `200`, 7883 bytes,
`<title>Cladding quotes from a 3D model — Concierge</title>`; `/studio/` and `trendibizz.com` still
200 after the recreate.

## 78. `caddy reload` cannot work on this box — recreate the gateway instead

**Cause.** The Caddy global block sets `admin off`, so nothing listens on :2019; `caddy reload`
fails with `dial tcp [::1]:2019: connect: connection refused` and the config is never applied.

**Fix (operational).** The Caddyfile is a bind mount: `docker compose … up -d --force-recreate

**Evidence.** Recreate applied the `/guide/*` route (public 200 immediately after).
