# Bug log — 2026-11-13 (session 20)

Required by the permanent bug rule in `~/.dsh/AGENTS.md` and the repo `AGENTS.md`: every defect
found is fixed, tested and documented in the same session. No "come back later". This file is the
record for this date. Each entry gives the cause, the fix, and the evidence that the fix works.

An entry is only closed when all three are present. Anything in the "Open" section is a bug whose
fix is blocked by something outside our control, with the blocker named — never a shrug.

## 1. SVG logos rendered without their lettering

**Cause.** `resvg` resolves an exact font family and never falls back. The container had no
`Liberation Sans`/`DejaVu Sans`, so `font-family="Arial,sans-serif"` produced a logo with the
wordmark silently missing. The old reader would have stored that blank image as "their logo".

**Fix.** `fonts-liberation` in `Dockerfile.api`, `resvg_py==0.5.0` pinned in
`api-requirements.lock`, and the reader *measures* whether text drew against a baseline forced to
use an impossible family, reporting "as intended" / "redrawn in a close match" / "words missing".

**Evidence.** `QA/verification/BRAND_FROM_SITE_2026-11-13.md`. With no font: wordmark 0 px of ink.
With the font: 512×137, 6043 bytes, 13,119 px of ink. Live container: all four trendibizz logos
render. 38 tests in `api/tests/test_brand_from_site.py`.

## 2. The reader claimed a colour from an image that never drew

**Cause.** Accent extraction ran on the rasterised bytes without checking whether the render
succeeded, so a blank logo could still yield a colour, and the screen said "found it" about an
image the customer would never see.

**Fix.** `render_logo_svg` returns the text state, and the accent is only proposed from an image
that actually contains the brand; otherwise the note says so plainly.

**Evidence.** Three specific honesty failures were reproduced against the real site and pinned in
`test_brand_from_site.py` (accent only from a real render; NZ inferred from page wording, not just
the TLD; the note no longer says "choose one below" when nothing rendered).

## 3. Deploy script rolled back a good deploy

**Cause.** `run_s20a.sh` ended on `docker logs | grep -ci traceback`, which exits 1 when it finds
nothing. The `ERR` trap fired on that success case and re-tagged `:vps` to the old image and copied
old files back, while the new container kept running.

**Fix.** No `ERR` trap in deploy scripts. Every check is explicit and sets `OK=0`; the script ends
on `RESULT: OK`. Written up in the handoff.

**Evidence.** `run_s20b.sh` and the later inline deploys: `RESULT: OK`, image id and running
container id compared and equal, health `healthy`, `social` recreated and attached.

## 4. The healthcheck re-emailed the same condition

**Cause.** `plan_notifications` (then inline in `main()`) keyed its "already told them" check on
`status|detail`. When the detail grew from `consent` to `consent,mailbox` the key changed and the
operator got another identical-looking `[Concierge FAIL] inbound:chain` email. Two arrived 20
minutes apart.

**Fix.** Claim on the status alone; a detail change updates what the next reminder says, silently.

**Evidence.** `api/tests/test_healthcheck_notifications.py`, 6 tests. Mutation check performed: with
the detail put back into the key, `test_a_wordier_detail_does_not_email_again` fails; restored, it
passes. Live after deploy: `state.json` keeps `last_sent` unchanged and no new email is sent.

## 5. Two portals demanded a password, and the sign-in asked for an unknown "Business ID"

**Cause.** Invitation flow required inventing a 12-character password typed twice, then signing in
with an email plus a Business ID the customer had never been shown. `/owner-ui` had its own

**Evidence.** `api/tests/test_passwordless_login.py` (9 tests). Live on the scratch

## 14. The Contacts tab returned 500

**Fix.** Repeat the subquery in the ORDER BY.

**Evidence.** Reproduced and fixed against a real Postgres 16 with the real `schema.sql`: old SQL

`scripts/verify/probe_owner_routes.py`.

## 18. The chat widget silently disappears on a site with a strict CSP

**Cause.** Our own site loads `widget.js` (200) and it requests `widget-config`, but the page's CSP

**Fix.** The widget injects no inline CSS at all now. Its stylesheet is adopted as a constructable
stylesheet, and the two remaining `style="..."` attributes were replaced with classes in that same

was weakened and every strict-CSP customer site is fixed too.

**Evidence.** Playwright console capture on https://trendibizz.com/:

```
Applying inline style violates the following Content Security Policy directive 'style-src 'self''
```

The CSP is served from `/website/site/_headers` inside the website container, which is **not in this
repo** — so it is also an instance of server drift.

**Evidence after the fix** (live, on the strict-CSP site): `#cc-root` present, launcher rendered
300x53, 1 adopted stylesheet, **0** inline `<style>` elements, **0** inline style attributes,
clicking the launcher opens a 264px composer. Tests: `api/tests/test_widget_csp_safe.py` (3),

## 45. Booking an appointment never created a customer

**Cause.** `app/booking.py` inserted a lead with the visitor's name, email and phone and never called
`casetimeline.reconcile`, so a person who booked an appointment was invisible in Contacts and their
appointment hung off an unlinked lead. Five enquiries were already in that state.

**Fix.** The booking path reconciles the customer before its transaction and stores `case_id` on the
lead, both for a new lead and an existing one.

**Evidence.** `tests/test_booking_creates_customer.py` (red when the reconcile is removed, mutation
checked). The five orphans were linked afterwards: `linked: 5 | still orphaned: 0`.

## 46. My CRM audit reported a gap that was not one

**Cause.** The audit joined inbound email drafts to `customer_cases.primary_email`. A person keyed by
phone (which is correct — phone is the stronger identity) therefore looked like an uncaptured email.

**Fix.** The audit counts enquiries whose **lead** reached a customer, which is the property that
matters. Also deleted two of my own `capture.email@portability.test` drafts left in the review tenant.

**Evidence.** Before: "10 received, 9 linked". After: "10 received, 10 linked", with no data changed.

## 47. Nothing stopped this recurring

**Cause.** The audit was a one-off run; the same defect could return silently.

**Fix.** `crm:capture` in the healthcheck fails when any lead has contact details but no customer.
Healthcheck went from 37 to **38 ok** checks.

**Evidence.** `python3 scripts/vps/healthcheck.py --no-alert` on the box: `counts ok 38, warn 1,
fail 1`.

## 48. Email signatures were read in one place only

**Cause.** `inbound_email.py` parsed the signature; `enquiries.capture` — the funnel every other
channel and every other caller goes through — did not. A forwarded message, an import or any future
caller would store the email and discard the name and company printed beneath it. Seen while seeding
test records: an email-channel capture produced a customer with no name.

**Fix.** Signature parsing moved into `enquiries.capture` for the email channel, filling only what
the message did not otherwise give.

**Evidence.** `test_an_email_signature_names_the_customer_from_the_shared_funnel` (red when the block
is removed, mutation-checked); the seeded record now reads "Sarah Whitfield · Acme Construction".

## 49. A booked appointment left the customer with no history

**Cause.** Booking created the customer, the lead and the appointment, and wrote nothing to
`case_events`. Contacts showed Tom Aitken with an appointment and **zero** events — the exact "customer
with no history" the CRM audit flags.

**Fix.** `booking.book` records a timeline event tied to the appointment id, tolerating failure so a
history write can never lose a confirmed booking.

**Evidence.** Seeded booking now reports `events: 1`; test asserts the event's `source_key` is tied to
the appointment.

## 50. My seed script bypassed the tenant loader

**Cause.** It read `tenants` with a raw `pool.fetchrow`, so `business_hours` arrived as a JSON string
and `booking.availability` died with `'str' object has no attribute 'get'`. Tooling, not product: the
real path uses `tenants._load`, which decodes it.

**Fix.** The script uses `tenants.get_by_id`. Recorded because a wrong way of loading a tenant is
worth knowing about, and it cost a deploy cycle to spot.
